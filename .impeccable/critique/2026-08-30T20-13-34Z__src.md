# Impeccable whole-platform critique — MET Mastery redesign

## Scope and evidence

This review covers the public landing handoff, authentication gate, student workspace, teacher workspace, learning/practice surfaces, mock-test surfaces, authoring/review tools, responsive navigation, accessibility semantics, design-system consistency, and performance signals.

Evidence used:

- Project context from `PRODUCT.md` and `DESIGN.md`.
- Static source review across `src/pages` and `src/components` (140 files).
- Impeccable detector run: 144 advisory findings, all in the `quality` category: 57 radius, 52 font-size, and 35 color findings.
- Existing successful lint/build evidence from the recent student-shell pass; the build still reports oversized chunks.
- The 16 Stitch reference screens previously exported for this project and visually inspected as reference material.

Not available in this session: live browser control or fresh screenshots of the current running app. Therefore responsive appearance, actual keyboard traversal, focus behavior, route persistence, and live async states are not claimed as browser-verified.

## 2. Design specificity verdict

### LLM assessment

The redesign has a real point of view. “Clinical Consult Room” is a good fit for a teacher-led exam-preparation platform: calm, precise, evidence-oriented, and less gamified than generic language-learning products. The strongest product-specific idea is not the color palette; it is the persistent teaching loop: diagnose a learner, assign targeted work, review evidence, and feed the next decision. That is a defensible product identity.

The weak point is system convergence. The 16 Stitch screens describe a cohesive visual family, but the source still reads as several products being brought together: a public static Stitch page, a React student shell, a teacher operations shell, a mock-test engine, authoring tools, and older/generated surface artifacts. The result is directionally branded rather than fully governed. A user can understand each screen, but may not consistently understand where they are in the larger product or which label is the canonical home for an action.

### Deterministic scan

The detector found 144 advisory findings across the page/component source:

- 57 radius advisories
- 52 font-size advisories
- 35 undocumented-color advisories

The highest-density files are `src/components/exercises/ShortAnswer.jsx` (27), `src/pages/mock-test-results.jsx` (20), `src/components/exercises/ExercisePlayer.jsx` (14), `src/components/exercise-player.jsx` (13), and `src/components/message-center.jsx` (9). This does not prove that every value is wrong. It does prove that the redesign’s visual grammar is not yet enforced at the point where the most consequential learning and review surfaces are built.

### Browser evidence

No live browser inspection was available for this critique. The Stitch references were inspected, but that is reference evidence, not proof that the current app matches them. The following remain unverified: desktop/mobile visual parity, overflow at real breakpoints, actual focus order, modal focus trapping, color contrast in rendered dark mode, browser back/refresh behavior, and end-to-end async recovery.

## 3. Overall impression

This is a strong product redesign direction with a medium-high implementation gap. The visual concept is substantially more distinctive and mature than a generic dashboard, and the teacher workflow is a genuine differentiator. The redesign currently optimizes individual screens more successfully than the transitions between screens.

The biggest opportunity is to make the learning loop the navigation model, not only a banner or workflow strip. A student should always know: what I need to do today, why it was assigned, what evidence will show improvement, and what happens next. A teacher should always know: which learner needs attention, what evidence exists, what decision is pending, and how that decision becomes the next assignment. The current platform contains these ingredients, but they are distributed across tabs, overflow menus, badges, cards, and route-specific implementations.

## 4. What is working

1. **The product has a credible ownable identity.** The teal/deep-teal/rust palette, serif display type, calm surfaces, and clinical tone fit MET preparation better than a loud gamified treatment.

2. **The domain workflow is visible.** `WorkflowStageStrip`, teacher Today/Workflow/Plan/Assess groupings, student progress/feedback concepts, and the diagnose → homework → feedback model give the system a meaningful backbone.

3. **The redesign shows serious accessibility intent.** Skip links, labeled nav landmarks, `aria-current`, menu roles, Escape handling, status roles, button semantics, lazy image loading, and reusable UI primitives are present. This is a good foundation; it needs whole-platform verification and consistency.

4. **The student shell’s recent corrections are sound locally.** The shell now has a clearer Stitch-aligned teal/rust hierarchy, a five-item mobile bottom nav, an explicit Start Practice action on desktop, a labeled sign-out control, and a dark-mode token override. Those improvements should become shared rules rather than remain isolated shell fixes.

## 5. Priority issues

### P1 — The platform has multiple visual and navigational products inside one product

**Evidence:** `src/App.jsx` sends the public experience to a static `/stitch/landing_page_master_the_met/code.html`, while authenticated students use `StudentDashboard`, teachers use `Shell`, and mock-test/authoring surfaces carry their own dense local systems. `src/components/shared.jsx` also retains legacy and new navigation maps. The detector’s spread across exercises, mock tests, messaging, and teacher authoring confirms the drift is structural, not limited to one shell.

**Why it matters:** The first login transition, student-to-practice transition, teacher-to-review transition, and mock-test transition are moments when trust is formed or lost. If the user feels they have entered a different product, the redesign will feel unfinished even when each page looks good.

**Fix direction:** Establish one platform contract for shell anatomy, page header, breadcrumb/back behavior, content width, panel hierarchy, action hierarchy, status messaging, and responsive navigation. Keep student and teacher role differences, but make them siblings of one system. Define one canonical token source and one canonical component layer; make legacy aliases explicit and temporary.

**Suggested validation command:** `/impeccable critique src/pages src/components src/styles` after the contract is applied, followed by fresh desktop/mobile captures of landing → login → student/teacher workspace.

### P1 — The information architecture is still too broad for the core jobs

**Evidence:** Student primary navigation exposes Home, Practice, Subjects, Homework, Feedback, and Progress, with Mock Tests, Resources, Messages, and Settings behind More. Teacher navigation exposes Today, Students, Calendar, Diagnose, Homework, Review, Resources, Mock Tests, Risk, and Operations, with additional settings overflow. The student code also has subject-specific destinations for reading, speaking, grammar, listening, writing, and vocabulary.

**Why it matters:** The user must remember the difference between a destination and a content type. For students, “Subjects” and “Practice” can both sound like places to start. For teachers, “Diagnose,” “Review,” “Risk,” “Operations,” and “Reports” can compete for the same attention. More menus solve space, but they hide the product model.

**Fix direction:** Reframe navigation around jobs and next actions. For students: Today, Practice, Assignments, Progress, and Help/Inbox may be enough, with subjects as filters inside Practice. For teachers: Today, Learners, Plan, Review, Library, and Insights may be a clearer top level, with Diagnose/Homework as workflow actions attached to a learner. Use explicit page subtitles such as “Practice by skill” and “Review submitted work” so labels do not carry the entire meaning.

**Suggested validation command:** `/impeccable critique src/pages/student-dashboard.jsx src/components/shared.jsx` plus a route inventory check for every destination reachable in one and two clicks on desktop and mobile.

### P1 — Async learning states need a single lifecycle language

**Evidence:** The code has Suspense fallbacks, loading labels, `window.toast`, error boundaries, retry reload, upload states, AI generation states, evaluation spinners, and empty states. They are implemented by many surfaces rather than one documented contract. The most consequential operations—generation, submission, scoring, review, and feedback—are distributed across `PracticeSession`, exercise players, homework creation, submission review, mock-test evaluation, and messaging.

**Why it matters:** In an education product, “did my work save?”, “is this score provisional?”, “what is waiting for the teacher?”, and “what should I do next?” are core product questions. A generic Loading… or success toast is not enough when an action changes the learner’s plan.

**Fix direction:** Define shared states: Draft, Saving, Saved, Submitted, Processing, Needs review, Reviewed, Failed, and Offline. Every long-running action should show current state, last successful save, safe retry behavior, and next action. Make provisional AI results visibly distinct from teacher-approved feedback. Persist drafts where loss would be costly.

**Suggested validation command:** `/impeccable critique src/components/PracticeSession.jsx src/pages/homework-create src/pages/submission-review.jsx src/pages/mock-test-eval.jsx` and then browser-test interrupted network, refresh during save, duplicate submission, and retry.

### P2 — Responsive and accessibility quality is not yet proven at platform scope

**Evidence:** The source has good semantic intent, but desktop and mobile shells use different navigation strategies. The teacher mobile shell reduces priority tabs to Submissions, Diagnostics, Dashboard and moves the rest to overflow; student pages use a separate bottom-nav strategy. There are many route-specific inline styles and local controls. Live browser verification was unavailable.

**Why it matters:** Responsive behavior is not just shrinking cards. Teacher review, exercise authoring, calendars, charts, audio controls, timed tests, and feedback text have very different failure modes on narrow screens. Keyboard users also need consistent dialog focus, menu focus, headings, and announcements across all of them.

**Fix direction:** Create a responsive matrix for each surface: navigation, header actions, tables, charts, editor, audio, timers, long text, and dialogs. Standardize focus management and live-region behavior in shared primitives. Test at 320, 375, 768, 1024, and wide desktop widths; include keyboard-only and reduced-motion passes.

**Suggested validation command:** `/impeccable critique src` plus Playwright captures and accessibility assertions for each role’s primary route and one representative learning activity.

### P2 — The design system is documented, but not yet authoritative

**Evidence:** `DESIGN.md` defines a useful token system, while the detector reports 144 deviations. The highest-density deviations are in core exercise and assessment surfaces. `src/components/shared.jsx` still contains inline style decisions, and `src/styles` has multiple layers including base, system, responsive, dark, redesign, and Stitch theme rules.

**Why it matters:** A redesign cannot stay coherent if every feature can add a new font size, radius, color, or surface treatment. Students will experience the drift as changing product personality; teachers will experience it as visual noise in high-density tools.

**Fix direction:** Make tokens executable: lint/scan allowed values, expose semantic roles instead of raw colors, and migrate the top-density files first. Decide whether Stitch tokens are the product tokens or a reference alias layer. Remove duplicate selectors only after behavior is captured in tests/screenshots.

**Suggested validation command:** `/impeccable critique src/components/exercises src/pages/mock-test-results.jsx src/components/message-center.jsx` and maintain a baseline that trends toward zero unexplained advisories.

### P2 — Performance risk is concentrated in feature-heavy surfaces

**Evidence:** The recent production build passed but warned about chunks over 500KB, including GrapesJS-related CSS/JS and a large Recharts chunk. The app does lazy-load many student pages, which helps, but the build warning indicates feature boundaries are not fully translating into delivery boundaries.

**Why it matters:** Slow first interaction is especially damaging for students on mobile networks and for teachers moving rapidly between review items. A polished shell cannot compensate for a delayed practice or submission screen.

**Fix direction:** Inspect the bundle graph, isolate visual-editor and chart dependencies behind route-level boundaries, avoid loading teacher-authoring dependencies for students, and measure first contentful/interactive experience for landing, login, student home, practice, teacher Today, and review.

**Suggested validation command:** `npm.cmd run build` with bundle analysis, then compare route-level network payloads on a throttled mobile profile.

## 6. Persona red flags

### Jordan — first-time student on a phone

The emotional promise is reassuring, but the IA may create hesitation: should Jordan go to Subjects, Practice, Homework, or Mock Tests? The mobile bottom nav prioritizes five items, yet important destinations are hidden. Jordan needs a single “next best action” with a reason and a clear return path after completing it. If a practice or submission is processing, the platform must say whether it is safe to leave.

### Sam — keyboard and screen-reader user

The source demonstrates strong intent with landmarks, skip links, labels, menu roles, and reusable controls. The risk is inconsistency across local dialogs, chart-heavy views, inline buttons, and route-specific controls. Sam needs predictable heading hierarchy, visible focus, dialog focus trap/restore, status announcements, and non-color-only meaning for scores, risk, and completion. This remains unverified without browser inspection.

### Alex — teacher managing several learners quickly

Alex benefits from the Today/Workflow/Review model and command palette, but the navigation still asks Alex to know which tool owns a task. Risk, Operations, Reports, Diagnose, Homework, and Review can fragment triage. Alex needs a single queue of decisions with learner context preserved across diagnosis, assignment, review, and follow-up. The current shell has the right ingredients but not yet the clearest operational center.

## 7. Cognitive-load analysis

**Intrinsic load:** High and appropriate. MET preparation, multiple skills, teacher review, provisional scoring, and learner evidence are inherently complex.

**Extraneous load:** Higher than necessary. Two role-specific shell systems, hidden overflow destinations, overlapping nouns, static-to-React handoff, and route-local visual conventions make users reconstruct the product model themselves.

**Germane load:** Strong potential. Progress graphs, teacher memos, workflow stages, practice by skill, feedback, and review evidence can help learners build a useful mental model. They need to be arranged around “what this means” and “what happens next,” not only displayed as dashboard content.

## 8. Emotional journey

The strongest peak is the moment a learner sees concrete progress or teacher feedback tied to a specific skill. The teacher equivalent is seeing a learner’s evidence turn into a targeted next assignment.

The main valleys are likely to be login handoff, long AI generation/evaluation waits, timed mock-test completion, and any submission where the saved/reviewed state is ambiguous. The current design has components to support these moments, but the product needs one emotional rule: uncertainty should always resolve into a visible status and a safe next action.

The end state should not be “you finished a page.” It should be “your next step is X,” for both student and teacher.

## 9. Minor observations

- The public landing route being a static Stitch HTML redirect is useful for preserving the reference, but it creates a product boundary that should be deliberately branded and tested as part of the login journey.
- Student tab state is held locally in `StudentDashboard`; durable URL-level deep linking and browser back/refresh behavior should be explicitly decided and tested.
- Feedback appears in both the primary student navigation and More-tab definition, which may be intentional for mobile/desktop behavior but is a sign that navigation ownership needs one source of truth.
- Teacher and student shells use different brand subtitles (“Teacher workspace” and “Student space”), which is good role signaling; their spacing, topbar actions, focus states, and responsive contracts should be visibly related.
- Mock-test result/evaluation surfaces contain many small local text sizes and colors. Some may be appropriate for dense data, but they should be semantic tokens with a documented exception rationale.
- A large amount of generated/reference material and historical artifacts is present in the worktree. Even when ignored at runtime, this increases the risk of visual/source drift and makes it harder to identify the canonical implementation.

## 10. Questions to resolve before the next redesign pass

1. Should the product’s primary navigation be organized around **roles and tools** or around the **diagnose → practice → submit → feedback learning loop**? My recommendation is the loop, with tools nested beneath it.
2. Is the public Stitch landing page the canonical production landing experience, or only a reference snapshot? This determines whether it should share the application token/component system.
3. Which state is authoritative when AI evaluation and teacher review disagree? The UI needs one explicit distinction between provisional guidance and teacher-approved feedback.
4. Which three student actions and three teacher decisions must always be reachable within one click on mobile? This should determine what stays visible instead of overflow-only.

## Bottom line

The redesign is worth continuing. It has a distinctive visual direction and a real instructional product model. The next phase should be convergence, not more screen decoration: one navigation grammar, one async-state language, one executable token system, and browser proof across the student and teacher critical paths. Until those are in place, the platform will look redesigned in places while still feeling assembled as a whole.
