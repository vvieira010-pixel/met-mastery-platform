# Impeccable critique — MET Mastery student-facing platform

## Scope and method

Target resolved to the current `src` student-facing surface, with `src/pages/login.jsx` as the live entry point. This is a critique only; no application source files were changed. The review used PRODUCT.md, DESIGN.md, representative React source, the current Stitch reference artifact, one deterministic detector run, and a read-only headless production check at https://met-mastery.vercel.app/?login=1. Native browser overlay tooling was not exposed in this session, so the visual evidence is screenshot and DOM evidence rather than an injected detector overlay.

## Executive read

MET Mastery has a credible, ownable product idea: a calm clinical workspace organized around a teacher-led learning loop. The strongest design decision is the promise that the system turns diagnosis into targeted practice and then into feedback. The redesign is visually recognizable, but the implementation still feels like a set of related surfaces rather than one governed platform. The login page is currently healthy enough to render, but it is compositionally wrong for desktop and has a real mobile sticky-header/autofocus collision.

## Design specificity verdict

The design has a real point of view. “Clinical Consult Room” is a good fit for MET preparation: calm, precise, evidence-oriented, and less gamified than generic language-learning products. The learning loop is the ownable idea, not merely the teal palette.

The main gap is convergence. The public Stitch experience, React student shell, teacher shell, mock-test engine, authoring tools, and exercise players each carry slightly different visual grammars. The result looks redesigned in places but assembled as a whole. The next design phase should be convergence around one navigation grammar, one card hierarchy, one async-state language, and one token source.

## Priority issues

### P1 — Desktop login composition is structurally collapsed

`src/pages/login.jsx:356-362` declares a responsive `md:flex-row` layout, then the inline style forces `flexDirection: 'column'`. The form and value proposition therefore stack at desktop, producing a long narrow page and weakening the intended “sign in plus immediate next-step explanation” relationship.

Fix: remove the conflicting inline direction override and make the responsive split explicit in the shared layout style. Keep the stack on small screens, but use two balanced columns at desktop with a deliberate max content height and vertically aligned focal points.

Suggested next command: `/impeccable polish src/pages/login.jsx` followed by 1440, 1024, 768, and 375px captures.

### P1 — Mobile sticky header overlaps the learning narrative

The header at `src/pages/login.jsx:312-331` is sticky, while the email field is autofocus-enabled at `src/pages/login.jsx:165`. On a 375px viewport, browser focus scrolls the form upward and the sticky header covers the bottom of the Learning Loop card.

Fix: choose one mobile behavior: remove autofocus below the desktop breakpoint, or add a scroll-margin/top offset and mobile-safe content padding. The header should never obscure the first explanatory block or the focused field.

Suggested next command: `/impeccable polish src/pages/login.jsx` with a mobile keyboard/focus pass at 320, 375, and 412px.

### P1 — Primary navigation is hidden rather than intentionally simplified

The public login header contains a permanently hidden nav and a permanently hidden Sign In link at `src/pages/login.jsx:329-336`. Only the logo and Get Started action remain. That makes the entry page feel unfinished and removes orientation for returning users.

Fix: either show a small, route-safe set of public links, or intentionally reduce the header to logo plus a visible “Sign in” state when already on login. Do not keep dead navigation markup hidden with both `hidden` and `display: none`.

Suggested next command: `/impeccable critique src/pages/login.jsx src/App.jsx` after deciding the canonical public routes.

### P1 — Submit ownership is duplicated

The form owns `onSubmit={handleSubmit}` at `src/pages/login.jsx:154`, while the submit button also prevents default and invokes `handleSubmit` at `src/pages/login.jsx:252-256`. This creates two submission paths for one user action and can cause duplicate requests or inconsistent event behavior.

Fix: make the button a plain `type="submit"`; keep validation and async submission in the form handler only. Add a one-request guard test for mouse click, Enter key, loading state, and retry after failure.

Suggested next command: `/impeccable audit src/pages/login.jsx` followed by the login interaction test.

### P2 — The design system is documented but not enforced

The detector found 358 findings, with the largest groups in color, radius, and font size. The spread across exercise players, mock-test results, messaging, and student/teacher surfaces is structural. Several sources also use gradients, glows, and one-off spacing directly in JSX.

Fix: define semantic surface/action/status tokens, migrate the highest-density files first, and document deliberate exceptions. Treat the Stitch CSS as a reference alias layer only if it shares the same token source as React; otherwise it will keep creating visual drift.

Suggested next command: `/impeccable critique src/components/exercises src/pages/mock-test-results.jsx src/components/message-center.jsx` and establish a baseline for unexplained advisories.

### P2 — Card hierarchy and spacing need one rule

The Stitch reference scan reports 5 nested-card, 14 cramped-padding, 6 side-tab, 2 low-contrast, and 1 dark-glow warning. In the live student home source, cards also combine rounded containers, border strips, translucent surfaces, blur, and local padding choices. The visual language risks making every block look equally important.

Fix: use one page surface, one primary panel level, and one secondary item level. Reserve colored edge markers for status only, remove decorative glows from high-density learning content, and keep text contrast at accessible levels. Verify the reference findings against the live route before broad cleanup.

## Persona red flags

- First-time student on a phone: the promise is reassuring, but the sticky-header overlap and the choice between Practice, Subjects, Homework, and Mock Tests create hesitation. The first action should be one obvious next step with a reason.
- Keyboard or screen-reader user: semantic intent is strong, but duplicate submit ownership, route-local controls, and unverified focus behavior create risk. Focus, status announcements, and error recovery need a cross-platform contract.
- Teacher working quickly: the product has the right learning-loop ingredients, but separate Diagnose, Homework, Review, Risk, Operations, and Reports concepts can fragment triage. The primary view should be a decision queue, not a tool directory.

## Minor observations

- The login footer still says © 2024; if this is production copy, it should be updated or made dynamic.
- “Get Started” appears in the header and inside the form without clarifying whether the paths differ.
- Student tab state is local in `StudentDashboard`; decide whether refresh/back/deep-link behavior is part of the navigation contract.
- The student shell has a good desktop sidebar and mobile bottom-nav foundation, but primary and overflow tab definitions should come from one source of truth.
- Inline visual decisions are numerous enough that future page work will reintroduce drift unless token linting or review gates are added.

## Overall impression

This is a worthwhile redesign direction with a medium implementation gap. The visual identity is credible and the instructional model is stronger than the surface polish alone. The next phase should not add more decorative cards. It should make the learning loop the navigation model: what is my next action, why am I doing it, what evidence will be produced, who reviews it, and what happens next?

## Questions before implementation

1. Should the login page use a true two-column editorial layout on desktop and a stacked layout only on mobile? My recommendation is yes.
2. For the public header, do you want visible product links, or a deliberately minimal logo + Sign in/Get started treatment?
3. Should the next implementation pass fix the four P1 issues first, or also begin the broader token/card convergence in the same change set?
