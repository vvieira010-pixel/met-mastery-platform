## Design Specificity Verdict

**LLM assessment**: The product is two distinct products sharing a shell. The inside (exercise player, mock test engine, teacher workflow) is deeply grounded in MET prep — the 12-type exercise switcher, cycle stage tracking, and diagnostic→homework→feedback loop are non-transferable. But the landing page is generic SaaS that could belong to any tutoring service. The teacher shell's nav (10+ items) and student dashboard (8+ parallel data hooks) show signs of feature accumulation without information architecture refinement.

**Deterministic scan**: 39 findings — 0 P0, 9 P1 (hardcoded colors in exercise components, Tailwind/CSS split), 22 P2 (missing focus states, duplicate tokens, contrast risks), 8 P3 (hardcoded spacing/font sizes). Biggest systemic issue: exercise components (ShortAnswer, Listening, ExercisePlayer) bypass the token system entirely with inline hex values.

## Overall Impression

The core product logic is strong — the teacher workflow is genuinely well-architected and the exercise engine is domain-specific. But the design hasn't kept pace with the engineering. Two styling systems coexist, the landing page feels like a different product, and the student experience has anxiety-triggering moments (blank loading states, failure framing). The single biggest opportunity: align the landing page visual language with the actual product inside.

## What's Working

1. **Diagnose→homework→feedback loop is architecturally enforced** — WorkflowStageStrip, priority sorting, and cycle-stage cards create a product-specific workflow that no competitor template would produce.

2. **Exercise engine is deeply considered for MET prep** — 12 exercise types with per-type interactions (MCQ elimination, blank fill, audio playback, speaking recording) represent real domain complexity handled with care.

3. **Teacher power-user layer** — Keyboard shortcuts + command palette + pending badges create an efficient workflow for the single-teacher deployment. This is where the product feels most polished.

## Priority Issues

### [P1] Two CSS systems coexist with conflicting values

**What**: tailwind.css defines `--radius-sm: 10px` while tokens.css defines `--radius-sm: 8px`. `--font-serif` maps to 'Merriweather' in Tailwind but 'Cormorant Garamond' in tokens. Every component is potentially inconsistent.

**Why it matters**: Every new component forces a choice between two systems, and developers will pick whichever they find first. The result is unpredictable rendering across the app.

**Fix**: Remove the `@theme` block from tailwind.css and use tokens.css as the single source of truth. Or migrate everything to Tailwind @theme and drop tokens.css. Do not maintain both.

**Suggested command**: `/impeccable harden`

### [P1] Student dashboard loads 8+ hooks simultaneously with no skeleton states

**What**: The student dashboard renders 8+ data hooks in parallel (homework, diagnoses, classEvents, reviews, submissions, practiceSessions, reviewCount, qpProgress) with no loading skeleton or staggered reveal.

**Why it matters**: The primary user is a nurse studying after a shift. A blank screen with no feedback is an abandonment trigger. The PageLoader exists in App.jsx but the dashboard renders its own empty state internally.

**Fix**: Add SkeletonCard/SkeletonText wrappers around each dashboard section. Show the learning loop immediately (it's static) while data loads behind it.

**Suggested command**: `/impeccable polish`

### [P1] Landing page visual language doesn't match the product inside

**What**: Landing uses raw Tailwind utilities, Feathericon SVGs, and generic SaaS copy. Inside, the product uses DM Sans tokens, custom Icon components, and clinical voice.

**Why it matters**: A nurse clicking "Book a diagnostic" then entering the product will feel a jarring disconnect. The landing page promises a different product than what they get.

**Fix**: Redesign landing hero to show a real product screenshot. Align copy to clinical voice. Replace Feathericon SVGs with the product's Icon component.

**Suggested command**: `/impeccable shape` or `/impeccable bolder`

### [P2] Teacher shell nav has 10+ items with no progressive disclosure

**What**: The nav surfaces Today, Students, Calendar, Diagnose, Homework, Review, Resources, Mock Tests, Risk, Operations, Settings. "Risk" and "Operations" are rarely accessed.

**Why it matters**: Product Principles say "Teacher workflow first" but the nav treats every feature equally. New teachers will default to clicking what they recognize, not what's next in their cycle.

**Fix**: Collapse Risk, Operations, Mock Tests, and Settings into a "More" group. Keep only Today, Students, Diagnose, Homework, Review, Resources in the primary nav.

**Suggested command**: `/impeccable distill`

### [P2] Exercise player frames failure as inevitable

**What**: "The correct answer is shown after N tries" appears on MCQ exercises. The countdown to answer-reveal creates pressure.

**Why it matters**: MET test-takers are anxious professionals. Framing failure as inevitable increases anxiety rather than supporting learning.

**Fix**: Reframe as "You can eliminate wrong answers. After trying all options, the correct answer is revealed for learning." Show remaining elimination attempts as progress, not failure.

**Suggested command**: `/impeccable clarify`

## Persona Red Flags

### Jordan (First-Timer)
- **No onboarding**: New students land on a dashboard with 8+ sections and no guidance on where to start
- **Exercise player ambiguity**: 12 exercise types with no explanation of what each does — Jordan will hesitate before clicking
- **Technical jargon**: "Cycle stage", "spaced-repetition", "error bank" appear without definition

### Sam (Accessibility-Dependent)
- **Inline-styled buttons override focus states**: shared.jsx, landing.jsx, and exercise components use inline styles that bypass the global `*:focus-visible` rule
- **Color contrast risk**: `text-white/50` on dark backgrounds may fail WCAG AA for small text (landing.jsx:202)
- **No screen reader announcements**: State changes (exercise submitted, recording started) don't trigger `aria-live` regions

### Riley (Stress Tester)
- **Exercise player fallback is silent**: If an exercise type fails to load, it renders with no error indication — Riley won't know what broke
- **Mock test state loss**: localStorage keys can be cleared independently, so test 2 could unlock while test 1 data is lost
- **No mid-test exit**: Mock test has no way to save and resume — a 2.5hr commitment with no escape

## Minor Observations

- Tooltip component injects a `<style>` tag on every render — extract to CSS
- App.jsx has hardcoded teacher emails (line 123-127) — should be env-only
- components.css is 7,788 lines — strong candidate for component-level CSS modules
- `--accent-light` is aliased to `--primary-light` in tokens.css — confusing naming when accent and primary diverge
- No `--success-hover`, `--warning-hover`, `--error-hover` tokens for interactive states
- Student dashboard useEffect calls getStudentSeedsStage but ignores the result — dead async call

## Questions to Consider

- If the teacher is the only user, why does the shell have 10+ nav tabs — are any of those actually used weekly?
- The student is a nurse studying after shifts. What happens when they open the app on a phone at 11pm with 20 minutes before bed — does the dashboard optimize for that session length?
- The exercise player has 12 types. How many are used in any single student's weekly homework? Could the player be simpler for 80% of sessions?
- The landing page converts via WhatsApp. Is the in-app experience designed to reduce WhatsApp dependency?
